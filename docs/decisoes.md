# Decisões de arquitetura (por quê)

- **Identidade própria (`app_user`), não o Firebase uid como PK.** Evita amarração ao provedor; trocar de auth mexe em uma coluna (`firebase_uid`), não no schema todo. `owner_id` é sempre o id interno.
- **Client-managed auth + JIT provisioning.** Front cria conta/loga no Firebase (SDK); senha nunca passa pela API; backend só valida JWT e provisiona `app_user` no 1º acesso. Sem Admin SDK.
- **Molde × lançamento separados, com snapshot.** `planned_amount`/`split_ratio_snapshot` copiados no `*_entry`, nunca FK. Base da imutabilidade: editar molde não reescreve o passado.
- **Imutabilidade por congelamento de pagos**, não por tabela de auditoria. Pago/recebido trava; unpay/unreceive descongela. Recálculo respeita o congelamento.
- **Sem entidades "a pagar/paga".** Estado é atributo (`paid`/`received`) do mesmo registro; duas tabelas criariam sincronização sem ganho.
- **A-receber dentro do `bill_entry`.** `person_id`+`received`+`received_date`; sem entidade de dívida. `paid` ≠ `received`.
- **Recebimento em lote, sem troco.** Valores exatos na prática; marcação em lote na UI, modelo continua conta-a-conta. Entidade de settlement descartada.
- **Orçamento anual, projeção idempotente.** UNIQUE(molde,ano,mês)+ON CONFLICT DO NOTHING; rerodar não duplica nem toca pagos. Virada de ano = projeção de ano+1 (default_amount já reflete reajustes).
- **Split como fração numérica** (não booleano). Cobre 1.0/0.5/0.0 e futuros sem refatorar.
- **Soft delete nos moldes.** Preserva integridade dos lançamentos históricos que os referenciam.
- **Isolamento na aplicação** (filtro por owner_id), não RLS — mais simples com EF Core. RLS fica para eventual multi-tenant sério.
- **Azure Web App F1 + Neon (pooler).** Free; ciente do cold start (migrar depois se incomodar). Neon pooler + SSL no EF Core.
- **Migrations aplicadas pela pipeline, não no startup.** `dotnet ef database update` roda no job `deploy` do CI/CD (usa a `AppDbContextFactory` já existente para tooling), não mais em `Program.cs`. Evita reaplicar a checagem de migration a cada cold start do Azure Web App F1 e separa responsabilidade de deploy da de runtime.
- **Todos os endpoints sob `/api/v1`.** Antes havia mistura: CRUDs na raiz (`/bills`, `/categories`...) e o resto sob `/api/...`, sem versionamento. Padronizado com um único `var v1 = app.MapGroup("/api/v1")`, sem extrair para extension methods por recurso (ganho baixo frente ao tamanho do `Program.cs` atual; fica como possível follow-up). **Cutover direto, sem aliases das rotas antigas**: como é uma aplicação de uso pessoal com deploy único (Azure Web App + Firebase Hosting controlados pelo mesmo owner), o custo de manter um grupo de rotas legado em paralelo (roteamento duplicado, risco de divergência) superou o benefício; a coordenação foi feita casando o merge deste PR com o da migração do frontend (`bills-frontend#43`) para o mesmo prefixo.
- **Clean Architecture em camadas (`Api` → `Application` → `Domain`, `Data` → `Application`/`Domain`).** Antes os endpoints acessavam `AppDbContext` e liam claims diretamente, misturando HTTP, regra e persistência. Agora: `Domain` (entidades encapsuladas, `Result`, cálculos puros) não depende de nada; `Application` define serviços (`IXService`/`XService` `internal sealed`) e as abstrações de repositório/`IUnitOfWork`, sem conhecer EF Core; `Data` implementa repositórios EF e o `AppDbContext` (filtro global por `owner_id`); `Api` só tem endpoints finos, contratos de request e o `UserEndpointFilter`, que provisiona o `app_user` just-in-time e define o owner da requisição. `Program.cs` é o único ponto da `Api` que conhece `Data` (composition root: DI e `IMigrationService`). Ganho: regra testável sem banco e sem HTTP, e um padrão único para novas features (ver `CLAUDE.md` › Arquitetura).
- **Contrato HTTP padronizado via `Result` → `ProblemDetails`.** Serviços retornam `Result`/`Result<T>` em vez de lançar exceção ou devolver `IResult`; o endpoint só chama `ToHttpResult()`. Mapeamento único: validação → 400 `ValidationProblem`; não encontrado → 404, conflito → 409, 401/403 → `ProblemDetails`; `Result` sem valor → 204; listas vazias → 204. **Breaking change para o frontend** (precisa ser tratada no `bills-frontend`): 400s que eram texto puro viraram `ValidationProblem` (JSON com `errors`), listas vazias passaram de `200 []` para `204` sem corpo, e pagar/receber um lançamento já congelado passou a responder 409.
- **Erros em ProblemDetails (RFC 9457).** Toda resposta de erro é `application/problem+json`, não só as que passam por `ToHttpResult`: `AddProblemDetails` (com `instance` = caminho e `traceId` para correlação com os logs), `UseStatusCodePages` para os 4xx sem corpo gerados pelo framework (401 do JwtBearer, 404/405 de rota, 415, 400 de binding) e `UseExceptionHandler` para exceções. O código estável do erro vai na **extensão `code`**, não em `title`: pela RFC, `title` descreve o *tipo* do problema e não deve variar por ocorrência, e clientes não devem depender dele; `detail` fica com a mensagem. O exception handler roda **só fora de Development**, para manter a página de exceção do desenvolvedor localmente; em produção (e no ambiente `Testing` dos testes de integração) o 500 é genérico, sem mensagem nem stack trace. O 400 de token ausente em `GET /bills/shared` passou a ser `ValidationProblem` (`errors.token`), validado no serviço como nas demais features. **Breaking change para o frontend**: quem lia o código do erro em `title` deve passar a ler `code`; respostas antes sem corpo (401, 404 de rota, 400 de JSON) agora têm corpo JSON.
- **Testes: NUnit 4 + NSubstitute no Microsoft.Testing.Platform, com CPM.** MTP (`global.json`) dá um runner mais leve e coverage via `Microsoft.Testing.Extensions.CodeCoverage` (`--coverage` no CI, sem VSTest/`Microsoft.NET.Test.Sdk`); versões de pacote centralizadas em `Directory.Packages.props` e configuração comum em `tests/Directory.Build.props`. **Um projeto de teste unitário por camada** (`Domain`, `Application`, `Api`, `Data` em `tests/UnitTests/`), espelhando `src/` e permitindo rodar só a camada alterada. **Um único projeto de integração** (`tests/IntegrationTests/Api.IntegrationTests`) contra Postgres real: o Respawn reseta o banco **uma vez por fixture** (isolamento por `firebase_uid` distinto em cada teste) e o assembly é `NonParallelizable`, porque fixtures em paralelo no mesmo banco teriam seus dados apagados pelo Respawn umas das outras.
